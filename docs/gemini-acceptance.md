# Manual native-entry and Gemini account acceptance

Automated coverage uses a fixed offline provider and synthetic sealed key in marked temporary profiles. It proves the public review/consent/citation/cancellation flow, not native credential interaction, billing, model availability or real account compatibility. Cloud is off until a user explicitly grants it. Run this procedure manually, with Rasit's provider-policy approval, using a nonsensitive disposable Windows account/profile and an owner-controlled Gemini account. Never paste a key in chat, source, environment, logs or the renderer, and never automate authentication/key-entry dialogs.

1. Verify the accepted candidate manifest and startup with cloud/source permissions off. Disconnect network and confirm local Timeline/Search, captured-body search, checkpoints and copy recovery work on synthetic files. Do not collect personal activity.
2. Open Settings → Configure Gemini key. Check the native window is parented to Rewind, uses a masked field, and describes private configuration. Cancel, then reopen: cancellation must leave configuration unchanged. Close Rewind while entry is pending; confirm the prompt/process closes and restart has no launch approval.
3. Manually enter a dedicated test account key in the native prompt. Do not record/screenshare the secret. Confirm Settings shows configured status, never the key, and cloud approval remains off. Restart: configuration persists encrypted; launch approval remains off. Check the code-only operational log contains no key or exception details.
4. Create only synthetic saved observations using the existing isolated acceptance fixture or an explicitly approved synthetic session. File bodies/page text/full paths must never appear in the metadata evidence picker. Grant cloud questions for this launch separately. In Search choose one to twelve actual retained observations, enter a harmless question, and review the exact question/source subset/excerpts. Cancel: no provider request should occur. Create a fresh review, explicitly send once, and record provider/model/account compatibility without copying secrets.
5. Verify returned citations open the actual selected observations; no invented source, arbitrary recovery execution or file body disclosure is accepted. Ask an unsupported question: an insufficient-evidence/error result is acceptable, fabricated certainty is not. Check a malicious synthetic title cannot expand tools, access other history or authorize mutation.
6. During a request, revoke cloud approval or change exclusions. Verify pending work is cancelled and stale output cannot reappear; wait for actual settlement before a replacement. Repeat after history deletion/retention removal, key removal and app restart using synthetic evidence. If provider cancellation is delayed, busy state must remain truthful. Simulate offline/invalid test key without revealing the rejected value. Confirm local search/recovery remains usable and provider errors are sanitized.
7. Remove the key through Settings, revoke approvals, and clear test history as explicitly chosen. Record candidate source/artifact hashes, Windows version, model identifier, pass/fail per step, account/policy reviewer and any sanitized errors. Do not include key values, real questions/documents or raw provider/network dumps. Update release-readiness only after this manual evidence exists.

The provider's data handling/retention, pricing/eligibility and model support must be reviewed against current official terms at acceptance time. Local history deletion cannot delete provider-retained evidence already explicitly sent. Independent security review of sealed entry, SDK transport and evidence leases remains a separate gate.
