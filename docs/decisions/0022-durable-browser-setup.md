# ADR 0022: Durable browser setup ownership and interruption handling

Status: implemented locally for Rasit's review. Utility bootstrap, actual desktop/browser discovery and public setup/permission/status/exclusion controls remain in progress.

## Ownership and publication

Registration values alone cannot establish ownership. Migration 008 adds one bounded browser setup journal to the existing encrypted database. It records immutable installation generation IDs, native directory/file identities, lengths and hashes, desktop image/source fingerprints, browser scope and a pending operation. No recording approval, capability, browsing metadata or generic executable/path command is included. Paths are derived within the main-owned private profile from validated UUIDs; stored identities still require current native revalidation before file use.

The journal uses a revision-checked transaction and confirmed readback. Receipt history is append-only and bounded to 128 generations / 256 KiB; registration pointers must reference owned browser scope and share one bridge generation. Pending operations include the previous registration pointers. Invalid state, stale revisions, replacement/removal of receipts and persisted grant fields are rejected. Startup verifies the journal before exposing storage; a missing or invalid row is not silently recreated. The checksummed migration creates the initial empty row once. Ordinary history retention/deletion preserves this operational ownership data, as it preserves privacy settings. Physical database accounting still includes it. Reaching the generation bound requires explicit future verified installation-file maintenance; it never authorizes deletion of unknown files.

The utility's installation publisher creates a fresh UUID directory below the private profile's `browser-host` directory. The existing native CREATE_NEW writer publishes the precompiled host, its bounded sidecar and the native host manifest without replacing a file. Approval belongs to the setup manager; sharing this primitive does not grant recovery or setup authority. Every file has native identity/hash/length readback. A bounded shallow native directory query holds root/ancestor leases, includes dot entries/directories and refuses reparse points; verification never uses an unguarded path enumeration before identity checks. Each content read again checks root/file identity, sharing, links, bytes and hash.

These installation files contain application code and necessary nonsecret host configuration, including image paths and the public extension origin. They do not contain history, document bytes, keys, approval or capabilities. They are ordinary application files, not encrypted captured evidence. The ownership receipt is encrypted. Failed publication or failed journal admission can leave an unused private generation; it is never registered or automatically executed, and unknown files are not removed as a cleanup fallback.

## Confirmed setup transaction

`BrowserSetupManager` is private utility composition, not an exposed renderer path/message API. Install, remove and repair require explicit confirmation. It first revokes approval, invalidates/drains collection and observes broker exit through its injected quiescence port. No generation is published if that prerequisite fails. It publishes/verifies new files, durably records a pending receipt, changes only owned registration and clears pending only after all requested operations and final journal persistence succeed. No method approves recording or resumes a session.

An interrupted/partial registration or failed final save leaves durable pending state. Startup is read-only and refuses to activate it. Explicit repair reuses the recorded generation instead of publishing another; native registration accepts an already-installed prepared path only with the prior ownership context. Competing mutations are bounded to one, stale startup proofs are fenced, and shutdown invalidates later steps and awaits in-flight work. Unconfirmed file-helper exit stays tracked for stop retry, blocks reuse and prevents a successful shutdown acknowledgement. A completed native mutation followed by shutdown/final-save failure remains pending rather than being reported as successful or silently rolled back.

Removal and update use the encrypted receipt to derive the previous manifest path. They need not open or execute old files to establish registry ownership: this permits removing a broken/missing installation while still refusing any registry value that differs from the owned path. New executable use always requires current file verification. Installer CLI execution comes from current verified application assets, never an old registry path. No registry tree is recursively deleted.

Startup verifies current installed files, registry views, extension identity, desktop image and native source/build identity before returning a private broker configuration. Registered browsers share one generation, so updating the bridge must include current registrations or explicitly remove them first. A removed browser is filtered out of private broker policy even if its browser retains an old host manifest. Existing native peer authentication then rejects it before exposing a connected channel. This does not depend on browser cache invalidation.

## Stable build identity

The Windows Framework compiler lacks a deterministic-build flag and can change PE timestamps without source changes. A build fingerprint hashes the native source files, compiler bytes and reviewed compilation flags, with checks before/after compilation. Each installed native byte hash is separately retained and always verified. Startup compares the source/build fingerprint for compatibility, so an independently compiled timestamp does not force setup again; changed sources/toolchain/flags or desktop image require an explicit update. This is local build consistency and encrypted receipt ownership, not a signed distribution or hostile same-user attestation claim. Build output also refuses redirected directories and linked native targets before compiler/Vite mutations.

## Evidence and remaining composition

Tests use generated files, marked temporary profiles and `com.rewind.test.<nonce>` keys only. Actual cipher tests cover pending/completed reopen, DB/WAL marker absence, retention/deletion, stale writes, immutable receipts, rollback/caller transactions, prior-schema upgrade and invalid/missing ownership startup refusal. Native publication tests cover bytes/identities, changed or replaced files, redirected directories, invalid inputs, real passive broker startup/shutdown and an actual journal → publication → temporary registration → shutdown/removal flow. Manager tests cover confirmation/order, all failure stages, explicit repair, broken-install removal, build changes, removed-browser filtering, shutdown and delayed startup races. Actual Chrome/Edge relay tests deny a browser excluded from the private broker even while its old host/sidecar remains.

These components still need worker/private bootstrap, main-owned image fingerprinting/discovery, public typed setup/permission/exclusion/status controls, renderer integration and packaged real-browser flow tests. Normal desktop browser recording remains unavailable until that composition passes. No production registration is performed by the agent, build or tests. Optional overwrite and conditional Gemini remain separate active goal work.
