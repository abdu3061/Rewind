# ADR 0018: authenticated local native relay and bounded client authority

17 November 2026. Implemented locally in layers under the core goal, pending Rasit's final technical review. The relay is verified with isolated browsers; normal application browser collection is not yet wired. Mohammad Poorhamadi owns transport; Rasit owns engine/privacy/composition; Hacer and Abdullah own its forthcoming integration/UI review.

## Native relay

The Windows helper compiles from bundled C# sources using the installed Windows compiler. No SDK/framework download or third-party dependency is added. A browser-launched host and a desktop-launched broker use the same known image, with distinct entry paths. They verify actual peer image/hash, token user, Windows session and parent relationships. Browser identity comes from the observed allowed Chrome/Edge executable and its trusted publisher, not an extension-declared browser string. Caller origins must exactly match the configured allowlist. The system command interpreter is supported as a bounded Chromium launch intermediary. Desktop/host configuration is strict, bounded and restricted to local fixed-drive image paths.

The broker owns an explicit private, remote-rejecting named pipe. Startup requires the first instance; subsequent listening instances are created while an owned accepted anchor remains open. Four clients and one listener are the complete native connection budget. A connected peer is published to Node only after host-image, signed browser-parent and origin checks. Browser bodies are relayed as bounded opaque payloads; captured text cannot become a private broker command. The Node utility still must validate final message schemas, source authorization, nonce, sequence and active session before persistence. Native authentication alone does not enable recording.

Frames use bounded little-endian lengths and strict UTF-8, with a 256 KiB limit. A partial-frame deadline ends the relay process: disposing a synchronous stdin handle is not a reliable way to cancel a blocked read. Fatal native acceptance/output errors also terminate the helper rather than advertising a dead listener. Process watches end broker/host relays when their observed parent/server dies, including while the main thread is blocked. No relay operation writes captured evidence or executes page content; EOF/shutdown closes owned streams. Failed transport can lose unconfirmed observations, never justify a fabricated persistence acknowledgement.

The helper is currently compiled for tests, not packaged/registered as a production feature. Installer/update ownership, private configuration publication and normal utility composition remain necessary. These process/path/hash checks are not protection against a compromised account, arbitrary application replacement, process injection or administrator control; release signing/security review remains independent work.

## Client authority protocol

Client messages advance to version 2 before operational integration. Hello binds a connection and profile ID; the broker supplies browser identity. Visits require an unpredictable capability in addition to session/generation/connection and increasing sequence. State replies carry revisions, exclusions and a bounded expiring authority; stop acknowledgements name their revision. Host/config authentication remains its separate version 1 layer. The old candidate protocol was never an operational deployed transport.

The metadata controller requires both extension approval and current desktop authority before calling its provider. It checks private/active/focused context and exclusions before titles, strips URL query/fragment, rejects credential URLs, bounds title size and deduplicates repeated observations. No DOM/article extraction, storage backlog or generic command API is added. A provider receives an authorization predicate to recheck between asynchronous browser API stages. Revocation/new generation invalidates results before returned tab fields are inspected; stop acknowledgement waits for pending work to drain. Bursts collapse to one request plus one follow-up. Expiry checks both wall and monotonic time; an expired connection requires a fresh handshake. Older state revisions cannot resurrect authority.

This controller is tested independently and remains unregistered in the inactive background script. The server lease issuer, real browser API adapter, consent UI, encrypted timeline admission and pause/end integration are still required before normal monitoring can be enabled.

## Verification and machine changes

Native unit tests compile actual executables and cover framing, bad configuration/callers, local origin claims from a wrong executable, partial-frame timeout, parent death and clean broker shutdown. Windows peer tests cover actual handles, SID/parent/session relationships, DACL/first-instance behavior and signed installed browser images. Client tests cover approval/lease conjunction, redaction, exclusions, private/focus guards, stale callback drain, generation changes, bounded bursts, expiry and send/query failures.

`npm run test:browser` uses installed Chrome and Edge with generated profiles and a tiny **synthetic probe** extension. Experimental DevTools unpacked loading is confined to those profiles. Each test creates a unique `com.rewind.test.<nonce>` per-user host registration, exercises authenticated bidirectional frames, disconnects/reconnects with fresh physical channel identity, then closes processes and removes the registration/profile. The probe requests no tabs, host permissions or DOM access and reads no real browsing history. Cleanup attempts registration removal even after browser/process errors; unrelated entries are never replaced. Both 32/64 registry views and the temporary-profile directory were checked afterward: zero matching leftovers. This is a relay test, not proof of the completed Rewind extension/recording pipeline.

Exact complete quality/build/app/browser results are in the [integration report](../audit/core-functionality-integration.md). Primary references: [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Edge Native Messaging](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging), [DevTools extension loading](https://chromedevtools.github.io/devtools-protocol/tot/Extensions/).
