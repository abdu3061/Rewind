# ADR 0017: verify Windows peer facts before browser authority

17 November 2026. Native browser work in progress. This implements tested primitives, not an authenticated operational browser bridge or an installed host. Rasit retains final review; Mohammad Poorhamadi owns transport integration.

The desktop composition contains a small C# source asset, matching the existing Windows-helper approach without a new dependency/framework installation. It obtains pipe peer PIDs from Windows, holds process handles, queries the executable path, token user SID, creation identity and direct parent, and checks liveness through the process object. An exited process with code 259 must not be mistaken for a live peer. Closing proof handles makes them unusable.

The local pipe primitive supplies an explicit protected DACL for the current user, denies network identities, rejects remote clients and uses FIRST_PIPE_INSTANCE to refuse a name collision. It does not rely on Windows' default pipe security descriptor. A connected peer can be resolved through either actual pipe end. These facts still need to be combined with expected host/desktop paths, image hashes, browser parent verification and fresh consent/session leases in the broker/host; a PID, SID, origin string or signed file alone does not grant collection authority.

Browser-image checks require the expected executable name, Windows Authenticode trust and the expected Google/Microsoft organization, while denying write/delete sharing during inspection. Trust retrieval uses the local cache and does not fetch over the network; missing trust fails closed. Image hashing is bounded. These checks do not claim protection against a compromised Windows account, injection into a trusted process, a malicious administrator or arbitrary replacement of the application. Final host packaging/registration and mutual protocol integration remain pending.

Five real Windows tests use generated fixtures and temporary pipes: actual parent/user/process facts, invalid/closed/exited identities including exit code 259, both pipe-peer APIs, inspected DACL and first-instance collision rejection, rejection of an installed runtime renamed to `chrome.exe`, and signature/hash verification of the locally installed Chrome and Edge executables. They do not launch a browser, read a browser profile/history, register a host or read personal documents. Test helpers run hidden and close owned resources. `npm run check` passed **233 tests / 33 files**, TypeScript, lint, formatting and install metadata after these additions. The native source is not yet referenced by runtime or packaged as a host; the previously rebuilt consent/checkpoint app passed all 12 packaged tests.

Primary API references: [named-pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [server peer process identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid), [WinVerifyTrust policy](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/ns-wintrust-wintrust_data). No origin allowlist, browser collection, nonce/sequence handling or extension permission is bypassed by this foundation.
