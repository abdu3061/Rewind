# ADR 0012: retention, quota and transactional snapshot storage

17 November 2026. Local implementation on `feature/core-functionality`, under the user's core integration goal. Proposed for Rasit's final review; no remote merge or release approval is implied.

The utility process remains the only production database owner. Retention uses the persisted hour setting (72 by default), checks at startup, before timeline retrieval and once a minute while open. Closing Rewind stops the maintenance timer; there is no hidden scheduled service. The cutoff is inclusive for retained evidence: records strictly older than the cutoff expire.

Kept checkpoints and their transitive version/visit references survive expiration and ordinary deletion. Recent unkept checkpoints also retain their referenced evidence until they expire; under quota pressure unkept checkpoints can be evicted. Session date/status shells and privacy settings remain after evidence deletion. The engine must stop and drain sources before explicit maintenance/deletion acknowledges; these operations revoke launch approval and never resume automatically.

Cleanup deletes relational records and derived FTS entries in a transaction. It checkpoints the encrypted WAL and uses VACUUM to compact after removal. Physical usage includes the database, WAL and shared-memory journal. Quota pressure evicts oldest unpinned records in bounded batches. If retained artifacts or database overhead still exceed the limit, collection admission fails and grants are denied. This is an application quota/backpressure policy, not a filesystem hard reservation: the last bounded write and compaction can temporarily use extra disk space. Full disk/busy/cipher/compaction failures return failure; committed logical deletions cannot be rolled back after a later compaction failure, and the result explicitly says so. No plaintext fallback or automatic deletion of kept evidence is allowed.

Migration 004 gives visit membership a real foreign key and validates same-session/type membership, refusing invalid historical links. Existing migrations stay checksummed and immutable. Session deletion is not exposed: its legacy cascading relationships must never bypass Keep.

For the upcoming snapshot slice, store bounded original bytes in an immutable content-addressed BLOB table in the existing verified encrypted database. SHA-256 binds bytes to metadata and is checked when reading. Deduplicate by hash; publish a blob, version, identity and observation in one transaction. This avoids a separate unencrypted blob path and a cross-store crash window. Cleanup removes unreferenced blobs transactionally with metadata; shared/kept blobs survive. Only versions with actual verified bytes appear as recoverable. Public DTOs never include SQL, keys or internal content locations. Large unbounded documents and external text parsers are outside the first capture implementation.

Windows file access requires handle-based path/identity checks and conservative sharing rules. Node path strings and before/after lstat alone cannot authorize a Windows recovery target. Reference: [CreateFileW sharing and reparse behavior](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew). Exact implementation and synthetic Windows tests must precede any overwrite capability.

Logical deletion, secure_delete, compaction and encrypted storage do not promise forensic erasure of SSD blocks, backups, swap, crash dumps or independently recovered/exported copies. DPAPI and these checks do not defend against a compromised same-user account. Independent security and distribution review remain release gates.
